# pgsql-hackers digest — Feb 16, 2026

1. **Out-of-cycle release scheduled for February 26** — Jonathan Katz announces an emergency release to fix two critical regressions from the February 12 update: substring() raising encoding errors on non-ASCII column data, and standbys halting with "could not access status of transaction" errors. Commits should follow standard guidelines leading up to the release. [link](https://www.postgresql.org/message-id/4746c150-0af6-4352-ac53-1415fa93fae9%40postgresql.org)

2. **Comments missing from publication/subscription psql output** — Fujii Masao proposes patches to add comment display to \dRp+, \dRs+, and \dX+ commands for consistency with other \d commands, and suggests trimming \dRs+ output which currently shows nearly all subscription parameters and will grow unwieldy as new columns are added to pg_subscription. [link](https://www.postgresql.org/message-id/CAHGQGwGL4JqiKA26fnGx-cTM%3DVzoTs_uzqejvj4Fawyr4uLUUw%40mail.gmail.com)

3. **Generating function defaults from pg_proc.dat** — Andrew Dunstan proposes eliminating the need to manually write default argument specifications in system_views.sql by having genbki.pl generate function_defaults.sql from new proargdflts/provariadicdflt fields in pg_proc.dat, making it closer to a single source of truth; the second patch converts 37 existing functions. [link](https://www.postgresql.org/message-id/183292bb-4891-4c96-a3ca-e78b5e0e1358%40dunslane.net)

4. **Race condition causes "relation deleted while still in use"** — Alexander Lakhin reports a buildfarm failure in 001_pgbench_with_server.pl where concurrent GRANT/VACUUM operations trigger "relation 266643 deleted while still in use" errors, providing a reproduction script that demonstrates the issue with 40 concurrent sessions. [link](https://www.postgresql.org/message-id/9f7cc148-55d1-4062-8229-b6886d7aa380%40gmail.com)

5. **HOT updates debate focuses on API boundaries** — Jeff Davis questions Greg Burd's placement of HeapDetermineColumnsInfo() logic in the executor rather than passing modified-index-attributes as an argument to table AM update calls, suggesting an extra bool parameter is better than moving code to the wrong side of an API boundary despite Burd's concerns about signaling and catalog-specific logic. [link](https://www.postgresql.org/message-id/fc17cbe85c24ff9d3cf43bfb37e6ca0d483fb2b4.camel%40j-davis.com)

6. **COPY's convert_selectively option unexpectedly exposed** — Sugamoto Shinya discovers that convert_selectively, intended as an internal file_fdw optimization, can actually be specified in SQL COPY commands (causing unconverted columns to become NULL), and proposes either updating the comment, blocking SQL access, or officially documenting it. [link](https://www.postgresql.org/message-id/CAAe3y%2B8J_uOp1B8Jrk1oKX2SNy9xSAcnpN6fKy%2BEpxq%3DMf1Kqg%40mail.gmail.com)

7. **Request to revert back-patched ABI breaks** — Peter Eisentraut requests reverting the CacheInvalidateHeapTupleInplace() and PrepareToInvalidateCacheTuple() signature changes from commits 06b030e and 2e58802 in the backbranches, arguing they are unnecessary ABI/API breaks that cause packaging pain for non-PGXN tableam modules with no real benefit. [link](https://www.postgresql.org/message-id/ff48df7b-8b82-4cf4-a340-668dadeff88f%40eisentraut.org)

8. **Exception handling for REFRESH PUBLICATION proposed** — Andrei Lepikhov proposes an exception_behaviour parameter for REFRESH PUBLICATION with values 'disable', 'retry', or 'skip', allowing bulk table synchronization to continue past individual table errors rather than stopping the entire subscription process when one of dozens of tables has a conflict or constraint issue. [link](https://www.postgresql.org/message-id/dc00ca44-48a7-49c5-ab4c-a60c8c5460ab%40gmail.com)

9. **OAuth2 infrastructure for token expiry tracking** — Ajit Awekar adds infrastructure to capture and store OAuth2 access token expiration timestamps in backend session state, noting that currently sessions can remain open indefinitely even after their authentication token expires; the patch does not implement enforcement policy yet. [link](https://www.postgresql.org/message-id/CAER375PhG5an%3Dp1%3D6QS6vWi%3DBHxR%2BViJmYPDkkEtpgVsfCcu_w%40mail.gmail.com)
