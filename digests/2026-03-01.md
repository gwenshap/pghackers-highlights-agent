# pgsql-hackers digest — Mar 1, 2026

1. **PLpgSQL FOREACH IN JSON ARRAY proof of concept** — Pavel Stehule implements `FOREACH x IN JSON ARRAY '[1,2,3]'` syntax that's 3-4x faster than `FOR IN SELECT FROM json_array_elements()` by eliminating SQL executor overhead; assigns JSON object fields to variables by name (not position since jsonb doesn't preserve field order), with open questions about whether default mapping should be lax or strict mode. https://www.postgresql.org/message-id/CAFj8pRD9Jjv%2Bm%3D6DP6vWWn5NnZeTPH9eoPFCnA1JE5hRKRDMxQ@mail.gmail.com

2. **REPACK memory leak and replica index handling bugs** — Mihail Nikalayeu finds memory leaks in attrs/isnull arrays, missing rd_pkindex fallback logic in rebuild_relation_finish_concurrent, and SHM_MQ_DETACHED handling issues in ProcessRepackMessages that could cause infinite waits; also questions whether indnkeyatts and index collation should be used instead of indnatts and heap collation in build_identity_key. https://www.postgresql.org/message-id/CADzfLwWC8gk5CPTjthN873KKGWsTqOnfEx2Z_2Nr6i%3DV8Y70Kw@mail.gmail.com

3. **Unlogged table fake LSNs fed to XLogNeedsFlush() in GetVictimBuffer** — Andres Freund discovers that GetVictimBuffer() reads LSNs from unlogged table buffers and passes them to XLogNeedsFlush() without checking BM_PERMANENT, which expects real LSNs; currently harmless since only bulkread strategies call StrategyRejectBuffer(), but could break if XLogNeedsFlush() gains LSN range assertions or tries to wake walwriter. https://www.postgresql.org/message-id/fmkqmyeyy7bdpvcgkheb6yaqewemkik3ls6aaveyi5ibmvtxnd@nu2kvy5rq3a6

4. **Clear pd_prune_xid when setting PD_ALL_VISIBLE** — Melanie Plageman proposes clearing pd_prune_xid whenever PD_ALL_VISIBLE is set to avoid confusing cases where all-visible pages retain prune xids, arguing that the next delete/update will set it again anyway; alternatively suggests WAL-logging pd_prune_xid in xl_heap_prune records to keep primary and standby values synchronized. https://www.postgresql.org/message-id/gwdfoam2qcdx3izhuiwypo4bnewddcxhir2nnyv4vihihu3i5j@4u2ybdwbhzqr

5. **Hash aggregate collision fix needs broader plan_node_id smearing** — Andres Freund notes that using `plan_node_id` alone as hash_iv is insufficient because some type hash functions have peculiar bit patterns; suggests combining it with use_variable_hash_iv and using better bit smearing, especially since hash-over-hash scenarios (like GROUP BY over GROUP BY, or CTAS of grouped data) could also suffer collision issues beyond just parallel aggregates. https://www.postgresql.org/message-id/ywqrfyzq77hxfvzj7kbm22dtcny3wqfm6gzwghorp2eq4kzzuf@af7v5atqoqk6

6. **pg_stat_statements_info should expose gc_count and query_file_size** — Lukas Fittl proposes adding two columns to pg_stat_statements_info: gc_count to show garbage collection cycles (which correlate with LWLock:pg_stat_statements waits), and query_file_size to help monitoring tools tune when to fetch query texts; both values are already tracked internally but not exposed for debugging large query text file issues. https://www.postgresql.org/message-id/CAP53PkzYZ8YxH0o%2BGarw9fWdFRoEtmQKT09-q%3D2RVMW8uVS5Nw@mail.gmail.com

7. **pg_buffercache_relation_stats() function for per-relation buffer summary** — Lukas Fittl adds pg_buffercache_relation_stats() which aggregates buffer cache statistics by relfilenode, returning counts of buffers, dirty/pinned buffers, and average usage count; existing pg_buffercache() approach takes 21ms vs 2ms for the new function on default 128MB shared_buffers, making it practical for monitoring which relations are evicted from cache on production systems. https://www.postgresql.org/message-id/CAP53Pkx0%3Dph0vG_M20yVAoK11yGSTZP%3D53-rZt36OCP4hBPaDQ@mail.gmail.com

8. **Reject ALTER DOMAIN ADD CONSTRAINT NOT NULL if name mismatches existing** — jian he proposes erroring out when `ALTER DOMAIN ADD CONSTRAINT NOT NULL` uses a different name than an existing domain not-null constraint, mirroring the table constraint behavior added in commit 96e2af60; repeated `ALTER DOMAIN SET NOT NULL` remains allowed since CREATE DOMAIN already disallows multiple NOT NULL constraints. https://www.postgresql.org/message-id/CACJufxEcTx2U8tQTcJ2g490wzd%3DjQgJNDpNb2L%2Bf3gr9J%3DcpNA@mail.gmail.com

9. **RI trigger batching helps I/O-bound workloads with prefetching** — Tomas Vondra tests Amit Langote's RI trigger batching patches with index prefetching and finds that batching alone gives 1.08x on I/O-bound workloads (161s→149s) but combined with prefetching yields 3.2x (→51s), because batching provides a window of upcoming probes for the prefetch machinery to issue readahead against; wonders if similar batching could help index inserts. https://www.postgresql.org/message-id/43b56e3b-80d6-4a45-a313-cb1caa587b22@vondra.me

10. **Tuple deformation patch has array bounds and alignment bugs** — David Rowley fixes issues found by Zsolt Parragi: first_null_attr() comment incorrectly removed requirement that at least one NULL exists, lastAttNum error check happened after out-of-bounds array access, nocachegetattr should use att_nominal_alignby instead of att_pointer_alignby, and typo in "This loops only differs". https://www.postgresql.org/message-id/CAApHDvpdBG-yzEbpy6qxVOcS3FtCt62Z%2B87G%3Dtww5Fg%2BAe0jBQ@mail.gmail.com
