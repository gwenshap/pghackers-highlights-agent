# pgsql-hackers digest — Feb 15, 2026

1. **NOT IN to anti-join optimization now handles multi-column comparisons** — Richard Guo posts v8 of the NOT IN sublink-to-anti-join patch, now extended to support RowCompareExpr for multi-column ordering operations (e.g., `WHERE (a,b) NOT IN (SELECT x,y ...)`), building on the earlier btree/hash opfamily safety checks. https://www.postgresql.org/message-id/CAMbWs4_V2QM%3DkUR3s3Jq8GVWAaZtouqpqU46GUuUXtCgAzBriA%40mail.gmail.com

2. **Inconsistent ownership between indexes and statistics objects** — Shin Berg reports that when a superuser creates an INDEX on another user's table, the table owner gets ownership, but STATISTICS objects remain owned by the creating superuser—causing operational friction when the table owner later needs to DROP the statistics but can't. https://www.postgresql.org/message-id/CACSdjfMWcR7aJUDf6XNt_yaDi%2Briz3Ku4EQ-x3xA%3DXx1209n2g%40mail.gmail.com

3. **Moving HOT decision logic into the executor** — Jeff Davis reviews Greg Burd's patch series to move HeapDetermineColumnsInfo() out from behind exclusive buffer locks into the executor, which would enable more precise HOT decisions (like when JSON documents have unrelated fields updated) and possibly improve concurrency. https://www.postgresql.org/message-id/3e1b9075c92808a7356e79087ba51910e5db5a30.camel%40j-davis.com

4. **substring() doing unnecessary work** — Thomas Munro proposes a simple patch to delete unnecessary computations in substring() following recent pgsql-bugs discussion, offering straightforward performance improvements. https://www.postgresql.org/message-id/CA%2BhUKGJCBvpSaiXkN%2BxJn1QcfpFnz%2BZntXdPb4BdzAUrqvFRfA%40mail.gmail.com

5. **64-bit interrupt masks need emulation to be signal-safe** — Andres Freund points out that the new 64-bit interrupt mask in Heikki's signal handling rework isn't safe because 64-bit atomics may be emulated with spinlocks, risking self-deadlock inside signal handlers; suggests splitting into two 32-bit words instead. https://www.postgresql.org/message-id/be6nxpkifw7kud4qxax4rzcfstg6r2uiynyugeu7jmxmbluy7b%404tnuf2khtmis

6. **MERGE doesn't check IsolationUsesXactSnapshot on TM_Updated** — Alexander Korotkov notices that ExecMergeMatched() checks isolation level in the TM_Deleted case but not TM_Updated, even though EPQ works at repeatable read; asks whether this is intentional or a bug. https://www.postgresql.org/message-id/CAPpHfdvzZSaNYdj5ac-tYRi6MuuZnYHiUkZ3D-AoY-ny8v%2BS%2Bw%40mail.gmail.com

7. **CREATE ASSERTION: Tom Lane explains why nobody implements it** — In response to interest in database-level assertions from SQL:2023, Tom Lane outlines the severe problems: terrible performance, deadlock potential, and the security concern that any user with read permission could block updates by creating assertions that fail. https://www.postgresql.org/message-id/812111.1771119222%40sss.pgh.pa.us

8. **Index prefetching benchmarks may miss OS cache effects** — Peter Geoghegan notices that Alexandre Felipe's index prefetching benchmark skips dropping OS caches (requires sudo), then shares his own results showing the patch causes small regressions even when data is fully cached, questioning whether the overhead is justified. https://www.postgresql.org/message-id/CAH2-Wzme0Gok57LkHEQQzNwJ%2BF2JK370yt5f2%3Dv6gOcOedgkpA%40mail.gmail.com

9. **Radix sort presorted check merged with common prefix detection** — John Naylor commits the v7 radix sort patch with renamed entry point (radix_sort_tuple), then posts v8 combining the presorted check and common prefix detection in a single loop to reduce memory reads and simplify the code. https://www.postgresql.org/message-id/CANWCAZaWV09%3DHdiF9mm7CBggFvxGkkHhhkSqyFoochQzW%3DRxAA%40mail.gmail.com

10. **Centralized CPU feature detection framework** — John Naylor proposes consolidating hardware detection logic (currently duplicated for CRC32C, popcount, etc.) into a single enum-indexed bool array before the AVX2 page checksum patch adds more; demonstrates that new features would need only 2 lines of code. https://www.postgresql.org/message-id/CANWCAZbgEUFw7LuYSVeJ%3DTj98R5HoOB1Ffeqk3aLvbw5rU5NTw%40mail.gmail.com
