# pgsql-hackers digest — Feb 24, 2026

1. **ProcWakeup() clears wrong waitStart field** — Chao Li catches a typo in ProcWakeup() where `pg_atomic_write_u64(&MyProc->waitStart, 0)` should operate on the parameter `proc` instead of MyProc, incorrectly clearing the caller's waitStart instead of the awakened backend's and potentially leaving stale values in the target PGPROC. https://www.postgresql.org/message-id/537BD852-EC61-4D25-AB55-BE8BE46D07D7@gmail.com

2. **pg_stat_replication lag shows NULL during active replication** — Shinya Kato reports that pg_stat_replication.*_lag sometimes shows NULL when startup process replays WAL before walreceiver sends flush notification, violating the assumption that two consecutive applyPtr==sentPtr messages must come from wal_receiver_status_interval; proposes checking all lag values are -1 before setting clearLagTimes. https://www.postgresql.org/message-id/CAOzEurTzcUrEzrH97DD7%2BYz%3DHGPU81kzWQonKZvqBwYhx2G9_A@mail.gmail.com

3. **Shutdown hang root cause is missing asyncXactLSN update** — Anthonin Bonnefoy traces the shutdown hang deeper and finds that XLogBackgroundFlush backs off to completed page boundaries, but uncommitted pages containing continuation records aren't flushed because asyncXactLSN isn't updated when transactions without xid are rolled back; proposes calling XLogSetAsyncXactLSN in RecordTransactionAbort even without xid. https://www.postgresql.org/message-id/CAO6_XqrZEREa5d%2BdyjahX6bteBhoN%3D8Jid-3a4f6Q35sWrv9eg@mail.gmail.com

4. **Remove array_ref() and array_set() wrappers** — David Geier proposes removing the array_ref() and array_set() wrappers (relicts from 2015) since only 5 calls to each remain on master, simplifying code by using array_get_element() and array_set_element() directly which take Datum arguments like most other array functions. https://www.postgresql.org/message-id/5bb669cc-7c48-4a50-b0b6-0612f95426d1@gmail.com

5. **Wrong results with grouping sets from unsafe RTE deletion** — Tom Lane flags commit ffe12d1d2 as unsafe because `list_delete_cell(query->rtable, lc)` changes rangetable indices of all following RTEs, which only appears to work if RTE_GROUP is always last; Richard Guo agrees and proposes converting the RTE into an innocuous RTE_RESULT instead. https://www.postgresql.org/message-id/3472344.1771858107@sss.pgh.pa.us

6. **Multixact OldestMemberMXactId array bounds bug** — Yura Sokolov reports that MaxOldestSlot calculation (MaxBackends + max_prepared_xacts) doesn't account for NUM_AUXILIARY_PROCS, causing writes to OldestMemberMXactId for prepared transactions to overflow into OldestVisibleMXactId or even BufferDescriptors; the bug was introduced in 2024 when dummyBackendId field was removed and replaced with pgprocno indexing. https://www.postgresql.org/message-id/7acc94b0-ea82-4657-b1b0-77842cb7a60c@postgrespro.ru

7. **REPACK CONCURRENTLY hits 1GB limit with wide rows** — Alvaro Herrera identifies a potential problem where store_change() in pgoutput_repack.c uses palloc() for the entire flattened tuple, which will fail if the sum of wide columns exceeds MaxAllocSize even if each individual column is under 1GB; also expresses concern about the memcpy() overhead. https://www.postgresql.org/message-id/202602241757.6ac3iss2u4vo@alvherre.pgsql

8. **synchronized_standby_slots inconsistent with quorum sync replication** — Satyanarayana Narlapuram reports that synchronized_standby_slots uses ALL-of-N semantics which blocks logical decoding when any physical slot falls behind, even when synchronous_standby_names is configured for quorum commit (ANY M of N); proposes extending the GUC to accept quorum syntax so logical decoding availability matches the DBA's intended commit guarantee. https://www.postgresql.org/message-id/CAHg%2BQDfU7rOebrLDESPpHSgdiadKbpCOmBokcbmM6Gr%2BA5VobQ@mail.gmail.com
